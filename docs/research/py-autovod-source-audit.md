# py-autovod source audit for live SupoClip ingest

Audited 2026-11-15 against `0jc1/py-autovod` main commit **`424f49815aba773c85cc8a7851ac52c6554dfa96`**, authored 2026-11-01. This is static source inspection plus current first-party documentation; no application, live capture, upload, or deployment was run. Links below pin repository evidence to that SHA.

**Finding: feasible with an ingest adapter, but py-autovod is not currently a live rolling-chunk producer.** Its recording command blocks until Streamlink exits; only then does it enqueue the file for conversion, transcription, clipping, and optional upload. This can happen after a premature disconnect as well as a normal stream ending; it is not tied to a verified broadcaster-offline event. A separate supervised Streamlink/FFmpeg producer is probably the smaller integration if SupoClip supplies downstream clipping. This last sentence is an engineering recommendation, not an implemented capability. [Recording lifecycle](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/stream_monitor.py#L81-L179), [processing lifecycle](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/processor.py#L34-L101).

## What the current code actually does

- **Platforms:** README advertises Twitch, Kick, and YouTube Live. Source additionally accepts `dlive` and `rumble`, constructing channel URLs for all five. These enum entries are not proof of working integrations. Current Streamlink 8.6.3 documents Twitch, Kick, DLive, and YouTube plugins; **Rumble is absent** from both its official plugin index and tagged plugin directory. Treat Rumble as unsupported out of the box. Kick requires a browser to solve its API challenge; YouTube’s Streamlink plugin supports live streams and excludes VOD/protected videos. [Project README](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/README.md#L13-L20), [enum and URL mapping](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/utils.py#L12-L28), [URL mapping](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/utils.py#L52-L72), [Streamlink index](https://streamlink.github.io/plugins.html), [8.6.3 plugin directory](https://github.com/streamlink/streamlink/tree/8.6.3/src/streamlink/plugins).
- **YouTube workaround is incomplete:** `download_video()` first resolves a direct URL using `yt-dlp --get-url -f best`, but the preceding live check and metadata fetch still call Streamlink on the channel URL. If that live check fails, the yt-dlp workaround is never reached. Platform success must be established with end-to-end captures, not inferred from README. [Live check and metadata](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/utils.py#L69-L128), [YouTube path](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/stream_monitor.py#L58-L110).
- **No chunk completion hook:** one Streamlink `-o` output file is named `.ts`; source is captured as emitted, rather than explicitly muxed to MPEG-TS. There is no segment command, closed-file callback, rolling buffer, overlapping-window assembler, or chat-velocity/audio-spike listener in the inspected source. The `chunk_size` in clip generation batches transcript candidates, not incoming video. Configured `split_into_parts`/`split_duration` have no implementation references. [Recorder](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/stream_monitor.py#L85-L137), [candidate batching](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/gen_clip.py#L118-L148), [configuration](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/default.ini#L46-L54).
- **Publishing is narrower than the configuration suggests:** dispatcher implements YouTube through the external `youtubeuploader` binary and rclone through `rclone copy`. `restream` is mentioned in config but raises unsupported-service error. Processor queues the full converted recording for upload; generated clip files are not submitted to the uploader. It does not implement TikTok/Instagram publishing. [Upload implementations](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/uploader.py#L12-L75), [queued file](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/processor.py#L68-L86), [clip extraction](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/gen_clip.py#L291-L330).

## Stack, installation, and reliability

Main declares **version 1.2.1, Python >=3.10, MIT**, with Whisper/faster-whisper, PyTorch, OpenAI client, yt-dlp, NumPy, and audio packages; FFmpeg and Streamlink are external executables. OpenRouter key enables its own AI clipping. Latest GitHub release is v1.2.1, published 2026-06-28, while **PyPI `autovod` still exposes 1.1.0**, uploaded 2026-01-19. Pin a source SHA when evaluating current behavior. [Project metadata](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/pyproject.toml), [license](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/LICENSE), [AI settings](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/settings.py), [release](https://github.com/0jc1/py-autovod/releases/tag/v1.2.1), [PyPI metadata](https://pypi.org/pypi/autovod/json).

The Dockerfile explicitly describes itself as temporary/nonworking and copies `requirements.txt`, which is absent at this SHA. README also tells users to install that absent file. Neither the Dockerfile nor installer provides rclone or youtubeuploader. Docker packaging therefore needs repair before the proposed shared-volume deployment can be accepted. [Dockerfile](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/Dockerfile), [root tree](https://github.com/0jc1/py-autovod/tree/424f49815aba773c85cc8a7851ac52c6554dfa96), [installer](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/install.sh), [README setup](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/README.md#L22-L35).

Existing reliability code is useful but insufficient for production live ingest:

- One monitor thread per streamer; polling/retry delay defaults to **120 seconds**, also slept after a capture exits. Nonzero Streamlink exit returns an empty path, leaving any partial recording unenqueued. Streamlink stderr is discarded. This creates observability/recovery gaps. [Monitor](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/stream_monitor.py#L110-L179), [delay config](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/config.ini#L7-L9).
- The single processing worker uses an **unbounded in-memory queue**, with no durable processing-job ledger. `_convert()` returns its target path without checking the FFmpeg return code. Processing can back up across all channels and be lost on restart. [Processor queue](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/processor.py#L22-L101), [conversion](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/processor.py#L123-L140).
- Upload worker does persist pending items to JSON, restores them on startup, and retries with exponential backoff (defaults: five attempts; 2/4/8/16-second waits). However snapshots contain only queued items, excluding the in-flight upload; concurrent enqueue/shutdown can persist a snapshot that omits that item. This is not a transactional job queue and provides no external-publication idempotency guarantee. A retry wait also blocks the single uploader worker. [Upload retry code](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/uploader.py#L215-L274), [persistence](https://github.com/0jc1/py-autovod/blob/424f49815aba773c85cc8a7851ac52c6554dfa96/src/uploader.py#L315-L366).

## Assessment of the proposed FFmpeg pipe

```sh
streamlink --stdout twitch best | ffmpeg -i pipe:0 -c copy -f segment -segment_time 600 -reset_timestamps 1 -movflags +faststart /shared/chunks/chunk_%03d.mp4
```

This is a plausible remuxing sketch, not a zero-loss service. Replace literal `twitch` with a channel URL. Stream-copy segments normally start on source keyframes, so 600 seconds is approximate; stream copy cannot insert keyframes. `reset_timestamps` makes per-file timestamps near zero, requiring separate global offsets. For inner MP4 options FFmpeg documents `-segment_format_options movflags=+faststart`. Faststart moves the MP4 index on finalization; it does not make a growing normal MP4 safe to read or survive an unclean stop. Do not queue a file on creation; wait for finalization and validate it. [FFmpeg segment and MP4 documentation](https://ffmpeg.org/ffmpeg-formats.html#segment_002c-stream_005fsegment_002c-ssegment).

**The “zero dropped frames/ad breaks” claim is contradicted by Streamlink’s own Twitch documentation:** it filters preroll/midroll ads by pausing output, then resumes with a stream discontinuity. It cannot restore program content that was not delivered during an ad. Current Twitch streams may be fragmented MP4 with nonzero presentation offsets, so a `.ts` suffix does not establish the actual container. Test timestamp/codec changes and discontinuities. [Official Twitch behavior](https://streamlink.github.io/cli/plugins/twitch.html#embedded-ads), [8.6.3 ad-filter implementation](https://github.com/streamlink/streamlink/blob/8.6.3/src/streamlink/plugins/twitch.py#L266-L283).

Streamlink has finite segment retries and read timeouts; its retry-open/retry-streams options concern opening/finding streams, not a guarantee of recovering every live frame after a disconnect. A supervisor must check both pipe processes, collect stderr, retry reconnects, record gaps, handle final partial segments, and use unique per-channel/per-session paths so index zero does not collide after restart. [Streamlink transport/retry options](https://streamlink.github.io/cli.html#stream-transport-options). These supervisor requirements are engineering conclusions from the process/timeout behavior, not functions present in the one-liner.

## Does a 90-second event-triggered export eliminate boundary cuts?

**It can solve the file-boundary problem if the exporter assembles one media window across adjacent chunks. The trigger alone does not.** For an event at 09:55, an export requiring post-event footage needs chunk 2; a finalized-only 10-minute chunk workflow may wait until approximately 20:00 before that footage is available. A live short-segment ring buffer or fragment-aware reader is needed for prompt exports. This latency conclusion follows directly from the proposed 600-second/finalized-file contract.

A correct event exporter must retain sufficient pre-event media, wait for required post-event media, map delayed chat/audio trigger timestamps into capture time, concatenate compatible neighbors or render across them, and deduplicate overlapping events. Trigger latency must fit the prebuffer: if the earliest required frame is `p` seconds before the event and detection arrives `d` seconds after it, retain at least `p + d` seconds of history, plus processing/scheduling margin. Audio spikes require analysis before ten-minute files close. Chat needs a separate ingestion source and timestamp model; py-autovod supplies neither. A fixed 90-second window can still truncate a longer setup/payoff or miss an event whose trigger never fires. Thus “eliminates boundary cuts completely” is justified only for the narrow storage-boundary issue after those mechanisms exist, not for complete editorial context or lossless capture. These are reasoning conclusions about the specified architecture, not claims measured in this static audit.

## Minimum useful integration

1. Replace `download_video()` with a supervised producer, or keep it as an archive path and create a lightweight separate ingest service. Disable py-autovod’s own clipping/upload path when SupoClip owns those stages.
2. Produce short finalized segments; use a manifest/finalization signal and a durable job ledger. FFmpeg writes segment list entries after writing the segment trailer, offering a useful completion signal; still validate the file before marking it ready. [Segment finalization source](https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/segment.c#L364-L473).
3. Persist session/channel identity, sequence, original media times, capture wall-clock correspondence, codec parameters, and known gaps. Retain neighbors for overlap/context; publish a finalized assembled window to SupoClip through its supported input contract.
4. Add bounded processing concurrency/backpressure, disk limits/retention, failed-job recovery, and publication idempotency. Fix the image and pin working tool versions. Establish live tests for preroll, midroll, reconnect, abrupt termination, codec/quality change, final partial chunk, and two concurrent channels before claiming unattended reliability.

Items 1–4 are proposed modifications. Neither repository source nor official tool documentation establishes a measured end-to-end latency, guaranteed ad-free capture, or zero frame loss.
