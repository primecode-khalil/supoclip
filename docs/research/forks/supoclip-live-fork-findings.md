# SupoClip live recording and archive fork findings

Checked 2026-11-16 Europe/Bucharest against upstream `main` [`e42e93b02873d29e2000a6a8235c10e23f8c99c9`](https://github.com/FujiwaraChoki/supoclip/commit/e42e93b02873d29e2000a6a8235c10e23f8c99c9). This is a targeted source audit supplement to the complete native-fork/branch inventory. It does **not** assert that every fork was run or every file in every branch was reviewed. No applications, platform uploads, paid models, or live captures were run.

## Finding and recommendation

There is an existing, source-confirmed continuous-capture implementation: **[`OPPAILUVR/supoclip`](https://github.com/OPPAILUVR/supoclip)**, branch `main`, SHA **`0092933e43ca48c31b60cce3e02eec1575613d33`**. It is a detached repository (`fork:false`), so enumerating only GitHub's SupoClip fork network misses it. Its source contains channel monitoring, FFmpeg rolling recording, an authenticated streamer-management UI/API, and automatic clipping. This is actual live capture, not a VOD-import feature.

Use it as a design/code reference, not as the production base. Keep current upstream SupoClip and selectively adapt the small recording/streamer-management parts, or keep recording in the external producer. OPPA's implementation has no full-stream archive, no rclone or py-autovod integration, no durable segment handoff, and material ownership, recovery, portability, and deduplication problems described below. Its alternative YouTube publisher should not replace current upstream's durable social queue.

## Reusable OPPA pieces

1. **Watch-list shape and simple UI.** The [migration](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/migrations/sql/20261113_0001_live_stream_monitoring.sql) defines user-owned streamers and events, with platform, URL, active flag, buffer length, score threshold, and task link. The [routes](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/api/routes/live_streamers.py#L20-L105) and [`/live` page](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/frontend/src/app/live/page.tsx) provide a concrete starting point. Ownership fixes and durable session/segment/archive fields are required.
2. **Detection-to-recorder skeleton.** [URL normalization and yt-dlp probing](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/services/live_stream_service.py#L415-L489) and the [monitor worker](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/workers/live_stream_worker.py#L31-L207) show the offline/live transition plumbing. Replace broad error-as-offline handling, add strict URL validation, and use durable session ownership/leases.
3. **One FFmpeg process writing segments.** [`start_buffer_recording`](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/services/live_stream_service.py#L703-L760) uses reconnect flags, codec copy, `-f segment -segment_time 60 -reset_timestamps 1`. This is a better controller skeleton than launching a fresh download for each chunk. It still needs finalized-segment detection, source-time metadata, archive acknowledgement before deletion, and restart handling. Codec-copy segment duration follows source keyframes, so 60 seconds is nominal.
4. **Closed-segment validation and short-window analysis.** The [analysis entry point](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/services/live_stream_service.py#L1098-L1188) omits the newest file and checks the remaining MP4 files with ffprobe before concatenating them. Reuse the concept while tracking completion durably and submitting finalized files through current SupoClip's upload/task API.
5. **Sentence-aware preroll/postroll.** [`apply_context_preroll_and_postroll`](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/services/live_stream_service.py#L289-L408) is a separable heuristic worth evaluating on real clips. Its English phrase list and fixed 25–58 second policy should be reviewed against current upstream's existing clip-boundary logic before porting.

## OPPA production blockers

### Archive and correctness

- **It intentionally destroys source footage.** [Rolling purge](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/services/live_stream_service.py#L765-L815) removes old segments; stopping the recorder recursively deletes the buffer. [Restart/orphan cleanup and the global 10 GiB quota](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/services/live_stream_service.py#L817-L895) also delete source segments without an archive acknowledgement. There is no rclone transfer, archive manifest, retained full recording, or remote-copy verification in these additions.
- **Deduplication confuses local window coordinates with source identity.** The [session](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/services/live_stream_service.py#L67-L84) keeps `analyzed_timestamps` only in memory, keyed by candidate `MM:SS_MM:SS` [inside the moving concatenated window](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/services/live_stream_service.py#L1334-L1368). The same real event changes coordinates as the window moves; unrelated later events can repeat the same local coordinates. This can both duplicate clips and suppress valid later clips. Restart loses the set. There is no durable chunk identity, UTC origin, or absolute stream interval stored with the clip.
- **A temporary probe error ends the session.** Probe exceptions return `is_live:false`; the [worker offline branch](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/workers/live_stream_worker.py#L168-L192) stops/deletes immediately. It does not distinguish offline from unknown, wait for consecutive failures, or drain/finalize the remaining tail before deletion.
- **Restart safety is absent.** FFmpeg ownership is in a process-local dictionary. A restart treats previous buffers as orphaned and purges them; no durable recorder PID/session lease or resumable archive state exists. Multiple live workers can each record/analyze the same database rows. Current upstream's per-task advisory locks do not protect this separate direct-SQL path.

### Security and service boundaries

- **Cross-user clip metadata exposure.** [The clips route](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/api/routes/live_streamers.py#L97-L105) authenticates but discards the user ID. [The service queries](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/services/live_stream_service.py#L653-L697) filter by streamer ID or `all`, without owner filtering. A signed-in user can request other users' live clip titles, reasoning, IDs, timestamps, and filenames. This finding concerns metadata; existing task-file routes retain their separate authorization checks.
- **URL validation needs replacement.** The YouTube branch [accepts strings containing `youtube.com` or `youtu.be`, and preserves the input if it contains `/live`](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/services/live_stream_service.py#L416-L433). It does not parse and allowlist the actual host. Sending that value to yt-dlp creates an avoidable arbitrary-fetch/SSRF surface. Do not reuse normalization unchanged.
- **API keys do not work on the new routes.** They call synchronous `get_authenticated_user_id`, which only checks signed frontend headers, rather than [the API-key-aware `resolve_authenticated_user_id`](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/auth_headers.py#L113-L136). An external recorder using the current documented Bearer API key cannot manage the watch list without changing authentication plumbing.
- **Pause/delete does not reliably stop the separate live worker.** API routes call `stop_buffer_recording` against the API process's in-memory map; [`start-local.sh`](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/start-local.sh#L110-L126) starts the recorder worker as another process. Its query later excludes inactive/deleted rows, but does not reconcile and stop sessions removed from that result. Also, stop occurs before the database owner-qualified delete/update. Use a worker-owned durable command/reconciliation mechanism.

### Compatibility and operations

- **Hardcoded local AI bridge.** Live clipping instantiates `AntigravityDirectModel` directly. [Its implementation](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/ai.py#L489-L559) expects desktop `agentapi`, `/Users/luv/.gemini/antigravity/...`, local daemon metadata, and transcript log files. It does not use current SupoClip's configured provider for this path. Local Whisper is also hardcoded to `base` and English. This is not portable to a standard current Docker deployment without redesign.
- **Separate blocking rendering path.** The async live service executes synchronous ffprobe/FFmpeg operations directly; Whisper is globally serialized. `asyncio.gather` across streamers does not make blocking FFmpeg work nonblocking. The 35-second poll delay starts after the whole cycle finishes. It bypasses current ARQ admission/backpressure, source storage, task checkpoints, and progress conventions.
- **Direct task/clip SQL needs adaptation.** The worker [constructs JSON task metadata with f-strings](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/workers/live_stream_worker.py#L59-L76), so quotes/newlines in a stream title or name can invalidate the JSON value. The service [writes generated clips directly and marks the task complete after each clip](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/services/live_stream_service.py#L1547-L1609), even while the capture continues. It uses hardcoded checkout-relative media directories rather than the current storage service. Prefer ordinary upstream tasks for each finalized chunk.
- **Newer upstream fixes would be lost by adopting the old base.** Notably, current upstream includes [PR #394](https://github.com/FujiwaraChoki/supoclip/pull/394)'s bounded Twitch/Kick fragment downloads, idle-versus-overall transfer clocks, shared byte budget, and redacted stage logging, which OPPA's older `stream_source.py` lacks. The wording “live download path” in that PR means the deployed production path, not continuous livestream recording.
- **Do not adopt the second publisher.** The [new scheduler](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/services/youtube_auto_scheduler.py#L45-L60) hardcodes a local PostgreSQL identity and globally scans generated clips, while the [headless uploader](https://github.com/OPPAILUVR/supoclip/blob/0092933e43ca48c31b60cce3e02eec1575613d33/backend/src/services/youtube_headless_uploader.py#L19-L80) uses one persistent browser profile/cookie file. Its title-based verification/re-upload loop and random “anti-shadowban” delays are not evidence of delivery safety or platform effectiveness. Current upstream already has account-scoped OAuth providers, durable social rows, ARQ scheduling, and uncertain-outcome handling.

No forks were created remotely, changed, published, deployed, or used to post anything during this research.
